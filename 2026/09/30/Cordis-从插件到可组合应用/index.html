Cordis 入门实战：从第一个插件到可组合应用

xiaoyan2026-09-302026-09-30

这是一篇使用教程：沿着“做一个问候应用”的主线，把插件、服务依赖、事件、配置、生命周期和热重载连成一张图。下一篇再讨论 Cordis 论文中的设计动机与机制；这里不把 API 现象当作论文结论。

示例基于 DeepSeek Harness 的 Cordis 教程，使用该仓库的启动器和包名，而不是任意独立 Cordis 项目的通用安装命令。无需模型密钥。

先看全貌：Cordis 负责什么？

假设你有三个功能：生成问候、记录问候、对外提供工具。直接互相导入实现，很快就会碰到“谁先启动”“替换实现后旧监听器怎么办”。Cordis 将这些问题分开：

5. 插件卸载时，资源由谁回收？

一次 apply 并非永久有效：配置变化、服务消失或热替换都会使插件卸载。已通过 Cordis API 注册的监听器和子插件会跟随所属插件清理；自己创建的定时器或连接则要交给 ctx.effect()。

可以用一条因果链记住这一节：

每次挂载的实例称为 fiber。常见状态是 PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED，而 apply 或配置校验失败会进入 FAILED。若有多个异步 disposer，不能假定它们会依次完成；确需严格串行时，把步骤放入同一个 disposer 并逐个 await。

6. 从两份文件走向完整应用

现在回看 cordis.yml：它同时说明装了哪些插件、给谁传配置；inject 定义运行条件，服务提供能力，事件解耦通知，effect 兜住卸载清理。这就是可组合应用的骨架。

使用相同的 node --import tsx ../../vendor/cordis/bin.js 命令保持进程运行，再编辑 greeter.ts 或 consumer.ts：HMR 会卸载旧实例、回收其 effect、再挂载新代码。这里 timer 是 HMR 自身的依赖；漏掉它时 HMR 可能一直 PENDING，看起来就像“热更新没反应”。logger-console 让 HMR 的日志可见。按 Ctrl-C 停止开发进程。

如果某插件始终没有输出，按这个顺序检查：

  1. 路径或包名是否可解析；模块无法解析时 Loader 可能只通过 logger 报告，早期日志还可能错过控制台导出器。
  2. 所需服务的提供方是否在配置里、是否自身也卡在 PENDING。不要靠调整 YAML 行序修复依赖。
  3. 配置是否校验失败、apply 是否抛错、配置项是否被 disabled: true 禁用。
  4. 若只改了配置却出现意外重挂载，检查配置项有没有稳定的 id。

7. 如何迁移到真实项目？

DeepSeek Harness 也按相同模型组合能力：例如工具插件声明 inject: ['tools']，通过 ctx.tools.register(...) 注册工具；监听 tools/result 的另一个插件可以观察结果，卸载时注册会撤销。不过 ctx.tools、defineTool 和模型调用流水线属于 Harness，不是 Cordis 核心 API。想亲手跑一个无需模型密钥的真实工具调用例子，可继续读官方教程第 7 章。

最后把本文六个概念串成一句话：Loader 根据配置挂插件；插件通过 ctx 提供服务和发出事件；inject 决定它何时能运行；fiber 表示它当前活到哪一步；effect 保证它离开时不留下旧资源。

参考资料：Cordis 教程目录 · 生命周期与 effect · 服务 · 事件 · 配置 · 组合与 HMR。
